# Advanced Docker Assignment: Build and Deploy a Multi-Tier Application

**Scenario:**

You are working as a DevOps Engineer in an organization that wants to deploy a multi-tier application using Docker. Your responsibility is to containerize the application, configure networking and persistent storage, optimize Docker images, and manage all services using Docker Compose.

## Task 1: Create Application Dockerfiles

1. Create a Java Spring Boot application with a Maven build.
2. Create a Dockerfile for the backend application.
3. Create a separate Dockerfile for the frontend using Nginx.
4. Create a Dockerfile for the database if using a custom database configuration.
5. Ensure each Dockerfile follows appropriate best practices.
6. Use CMD and ENTRYPOINT wherever appropriate.

## Task 2: Implement Multi-Stage Docker Builds

1. Modify the backend Dockerfile to implement a multi-stage build.
2. Use Maven and JDK in the builder stage to generate the JAR file.
3. Use a lightweight Java JRE image in the runtime stage.
4. Ensure Maven and unnecessary build dependencies are not included in the final image.
5. Create another single-stage Dockerfile for the same application.
6. Build both images and compare their sizes.

**Challenge:** Optimize the final image size without affecting application functionality.

## Task 3: Configure Docker Networking

1. Create at least two custom bridge networks.
2. Configure frontend and backend communication through the appropriate network.
3. Configure a separate database network.
4. Ensure the frontend cannot directly communicate with the database.
5. Use container names or Docker service names instead of hardcoded IP addresses.
6. Verify connectivity using Docker networking commands.

**Challenge:** Disconnect a container from its network and troubleshoot the communication issue.

## Task 4: Configure Docker Volumes and Persistent Storage

1. Create a named volume for the MySQL database.
2. Mount the named volume to the appropriate database directory.
3. Configure a bind mount for application configuration files.
4. Insert sample records into the database.
5. Stop and remove the database container.
6. Recreate the database container and verify that the records are still available.
7. Take a database backup and demonstrate the restore process.

**Challenge:** Demonstrate data recovery after deleting and recreating a container.

########## Task 5: Implement Docker Compose ##############

1. Create a `docker-compose.yml` file to manage the frontend, backend, and database.
2. Configure each service to use its respective Dockerfile.
3. Configure custom networks.
4. Configure named volumes and bind mounts.
5. Use environment variables through a `.env` file.
6. Configure service dependencies using `depends_on`.
7. Implement health checks for the database and backend.
8. Configure restart policies.
9. Configure port mappings wherever required.

**Challenge:** Start and stop the complete application using Docker Compose commands without manually managing individual containers.

## Task 6: Image Management and Registry Integration

1. Build Docker images for frontend and backend.
2. Tag images using appropriate version numbers.
3. Push images to Docker Hub or Nexus Repository.
4. Pull the images from the registry on another machine.
5. Run the application using the pulled images.

**Challenge:** Implement version-based image tagging such as `v1`, `v2`, and `latest`.

## Task 7: Container Security and Optimization

1. Run application containers using non-root users wherever possible.
2. Create a `.dockerignore` file.
3. Avoid hardcoding credentials in Dockerfiles.
4. Use environment variables or Docker secrets for sensitive configuration.
5. Configure CPU and memory limits.
6. Scan Docker images for vulnerabilities using an image scanning tool.
7. Analyze and optimize image sizes.

## Task 8: Troubleshooting and Production Scenarios

Demonstrate the following scenarios:

1. Backend cannot connect to the database. Identify and resolve the issue.
2. Database container is deleted. Recover the application data.
3. Backend container crashes. Configure and verify automatic restart.
4. Frontend cannot communicate with the backend. Troubleshoot networking.
5. A new application version is released. Deploy the new image without rebuilding the database.
6. Demonstrate rollback to the previous application version if the new version fails.

## Submission Requirements

Students must submit:

1. All Dockerfiles.
2. `docker-compose.yml`.
3. `.env.example` without actual credentials.
4. Application source code.
5. Docker network and volume configuration.
6. Image build and registry commands.
7. Screenshots of successful deployment and testing.
8. Architecture diagram showing containers, networks, and volumes.
9. Documentation of troubleshooting scenarios and their solutions.

**Expected Outcome:**

At the end of this assignment, you should be able to design, build, deploy, manage, troubleshoot, and optimize a multi-tier application using advanced Docker concepts.

# Assignment: Deploy an Application on AKS Using Terraform, ACR, and Blue-Green Deployment

**Objective:** Provision an Azure Kubernetes Service (AKS) cluster using Terraform, deploy a containerized application from Azure Container Registry (ACR), and implement a Blue-Green Deployment strategy to release a new application version.

### Task 1: Provision the AKS Cluster Using Terraform
- Write Terraform configuration files to provision an AKS cluster in Azure.
- Configure the cluster with a minimum of **2 worker nodes**.
- Initialize Terraform and execute the `plan` and `apply` commands.
- Verify that the AKS cluster is successfully created and accessible.

### Task 2: Build and Push the Application Image to ACR
- Create a custom Docker image for your application.
- You can either build a new application image or reuse the image created in the previous Docker assignment.
- Create an Azure Container Registry (ACR), if one does not already exist.
- Tag your Docker image appropriately and push it to ACR.
- Verify that the image is available in your ACR repository.

### Task 3: Deploy the Application on AKS
- Connect to your AKS cluster using `kubectl`.
- Create Kubernetes manifest files to deploy your application using the image stored in ACR.
- Configure the required Kubernetes resources, such as:
  - Deployment
  - Service
- Apply the manifest files and verify that the application is deployed successfully.
- Check the Pod status, Service configuration, and application accessibility.

### Task 4: Implement Blue-Green Deployment for Application V2
- Make changes to your application code and create a new version (**V2**).
- Build a new Docker image with an updated version tag.
- Push the V2 image to ACR.
- Implement a **Blue-Green Deployment strategy** on AKS:
  - **Blue:** Existing application version (V1).
  - **Green:** New application version (V2).
- Deploy V2 alongside V1 without interrupting the existing application.
- Verify that V2 is working correctly.
- Switch the Kubernetes Service traffic from V1 (Blue) to V2 (Green).
- Validate that users are accessing V2 successfully.
- Ensure you understand how to roll back to V1 if any issues occur.

### Expected Outcome
By completing this assignment, you should be able to:
1. Provision an AKS cluster using Terraform.
2. Build, tag, and push Docker images to Azure Container Registry.
3. Deploy containerized applications on AKS using Kubernetes manifest files.
4. Implement Blue-Green Deployment to release application updates with minimal downtime.
5. Switch traffic between application versions and perform a rollback when required.

**Submission Requirements:**
- Terraform configuration files.
- Dockerfile and application source code.
- Kubernetes manifest files.
- Screenshots of the AKS cluster, ACR repository, and running Pods.
- Evidence of successful Blue-Green deployment, traffic switching, and rollback.

# Assignment: Design and Implement an Enterprise DevSecOps Pipeline Using SonarQube and Nexus

## Business Scenario

You are working as a DevOps Engineer in a fintech organization developing a Java-based payment application.

The organization wants to implement a secure CI/CD pipeline where every code change is analyzed for quality and security before it is released.

The organization has the following requirements:

- SonarQube must analyze source code quality and security.
- Nexus Repository must manage application artifacts and Docker images.
- Vulnerable dependencies must be identified before publishing artifacts.
- Only applications passing the defined Quality Gate should be published to Nexus.
- Different artifact versions must be maintained for development and production.
- The entire process must be automated using GitHub Actions or Jenkins.

## Task 1: SonarQube Advanced Configuration

1. Deploy SonarQube on an Ubuntu VM or using Docker.
2. Integrate SonarQube with your GitHub repository.
3. Configure a project with a unique project key.
4. Generate and configure SonarQube authentication tokens securely.
5. Configure a Quality Gate with the following conditions:
   - New code coverage should be at least 80%.
   - No new Blocker or Critical issues.
   - No new security vulnerabilities.
   - No new security hotspots left unreviewed.
6. Configure Quality Profiles for Java.
7. Configure branch analysis for main and feature branches.
8. Configure Pull Request analysis.
9. Integrate SonarQube Quality Gate with your CI/CD pipeline.
10. Demonstrate how the pipeline behaves when the Quality Gate fails.

**Expected outcome:** The pipeline should stop artifact publishing if the Quality Gate fails.

## Task 2: Nexus Repository Advanced Configuration

1. Deploy Nexus Repository Community Edition.
2. Configure the following repositories:

   - maven-releases (Hosted)
   - maven-snapshots (Hosted)
   - maven-central (Proxy)
   - maven-public (Group)
   - docker-hosted (Hosted)

3. Create separate users for developers and deployment pipelines.
4. Configure role-based access control.
5. Configure Maven settings.xml.
6. Configure pom.xml with distributionManagement.
7. Upload JAR artifacts to Nexus.
8. Configure release and snapshot artifact publishing.
9. Configure Docker repository authentication and connector.
10. Push and pull Docker images from Nexus.

**Expected outcome:** Nexus should act as the centralized artifact repository for the organization.

## Task 3: Implement Vulnerability Scanning

Integrate vulnerability scanning into your CI/CD pipeline.

Requirements:

1. Integrate OWASP Dependency-Check with Maven.
2. Identify vulnerable third-party dependencies.
3. Generate an HTML vulnerability report.
4. Configure the pipeline to fail if a dependency has a CVSS score of 7 or higher.
5. Generate a Software Bill of Materials (SBOM).
6. Scan the generated Docker image using Trivy.
7. Publish security reports as GitHub Actions workflow artifacts.
8. Ensure vulnerable artifacts are not published to Nexus.

**Expected outcome:** No artifact should be published when it violates the defined security policy.

Note: SonarQube code analysis and dependency/container vulnerability scanning are separate security controls. Use the appropriate scanner for each.

## Task 4: Build an End-to-End CI/CD Pipeline

Implement the complete workflow using GitHub Actions or Jenkins.

Pipeline stages:

1. Checkout source code.
2. Compile the Java application.
3. Execute unit tests.
4. Perform SonarQube analysis.
5. Wait for SonarQube Quality Gate result.
6. Perform dependency vulnerability scanning.
7. Generate SBOM.
8. Build the JAR package.
9. Publish approved JAR to Nexus.
10. Build Docker image.
11. Scan Docker image using Trivy.
12. Push approved Docker image to Nexus.
13. Generate and publish pipeline reports.

**Important condition:** The pipeline must not publish artifacts if any mandatory quality or security gate fails.

## Task 5: Implement Artifact Version Management

Create a version management strategy.

Requirements:

1. Publish development builds as snapshot versions.
2. Publish production builds as release versions.
3. Maintain unique versions for every production release.
4. Prevent accidental overwriting of released artifacts.
5. Maintain traceability between Git commit, JAR version and Docker image tag.
6. Demonstrate downloading an older artifact from Nexus.
7. Demonstrate rollback to a previous application version.

Example:

- Development: 1.0.1-SNAPSHOT
- Release: 1.0.0
- Release: 1.0.1
- Release: 1.1.0

## Task 6: Implement Branch-Based Pipeline Strategy

Configure the pipeline for the following branches:

**Feature branch**
- Build and test.
- Run SonarQube analysis.
- Perform dependency scanning.
- Do not publish production release artifacts.

**Main branch**
- Execute all quality and security checks.
- Publish approved release artifacts.
- Build and publish Docker images.

**Pull Request**
- Execute code quality checks.
- Perform security analysis.
- Prevent merging when mandatory checks fail.

## Task 7: Advanced Troubleshooting Scenarios

Demonstrate how you would troubleshoot the following scenarios:

1. SonarQube analysis succeeds, but the Quality Gate fails.
2. SonarQube scanner cannot connect to the SonarQube server.
3. Maven cannot download dependencies through the Nexus proxy repository.
4. Jenkins/GitHub Actions receives HTTP 401 while uploading artifacts to Nexus.
5. Nexus returns HTTP 403 during artifact deployment.
6. Two builds attempt to publish the same release version.
7. Nexus disk usage reaches 90%.
8. A vulnerable dependency is identified after an artifact has already been published.
9. Docker image push to Nexus fails due to authentication or TLS configuration.
10. SonarQube analysis reports different results between local and CI environments.

For each scenario, provide:
- Root cause.
- Diagnostic commands or logs.
- Resolution steps.
- Preventive measures.
